# AI Pool 前端体验与功能优化路线

> 目标：优先提升前端体验、减少卡顿、降低用户认知负担；在不盲目堆功能的前提下，把 AI Pool 从“功能可用”打磨成“稳定顺手的 AI 工作台”。
>
> 范围：聊天页、输入区、消息渲染、文件体验、模型选择、技能入口、会话管理、用户中心与后台能力。

---

## 1. 总体判断

AI Pool 当前已经具备多模型聊天、文件理解、图片生成/编辑、PPT、技能、模板、分享、计费等基础能力。下一阶段最重要的不是继续堆大功能，而是：

1. **聊天主链路更快**：长会话、流式输出、Markdown、代码块、文件预览不应造成明显卡顿。
2. **状态更清楚**：上传、解析、检索、联网、生成、失败、重试都要有稳定可见的状态。
3. **选择更简单**：模型、技能、文件、会话太多时，需要推荐、筛选、收藏、最近使用。
4. **体验更像工作台**：会话管理、文件引用、技能执行、用量统计要服务真实生产场景。

一句话：

> AI Pool 下一阶段应从“AI 聚合平台”升级为“低卡顿、状态清晰、可持续使用的 AI 工作台”。

---

## 2. P0：前端性能与体验稳定专项

### 2.1 聊天消息列表性能

#### 当前风险

聊天页是最高频入口，容易因为以下原因卡顿：

- 长会话导致 DOM 节点过多。
- 流式输出频繁触发父组件重渲染。
- Markdown / 代码高亮 / 表格 / LaTeX 重复解析。
- 文件卡片、图片预览、搜索来源、思考块同时渲染。
- 滚动状态和消息状态耦合，导致跳动或无法稳定贴底。

#### 优化方向

| 优化项 | 说明 | 优先级 |
|---|---|---|
| 消息列表虚拟化 | 只渲染视口附近消息，历史消息按需挂载 | P0 |
| 流式消息局部更新 | token 更新只影响当前 assistant message，不牵动整个 chat page | P0 |
| Markdown 渲染缓存 | 按 `message_id + content_hash` 缓存解析结果 | P0 |
| 代码块懒渲染 | 长代码、diff、JSON 展开或进入视口后再高亮 | P0 |
| 附件预览懒加载 | 图片、PDF、文件预览进入视口后再加载 | P0 |
| message item memo | `MessageItem` / `MarkdownRenderer` / `CodeBlock` 组件 memo 化 | P0 |

#### 验收标准

- 200 条以上历史消息滚动仍流畅。
- 流式输出时输入框不抖动、不失焦。
- 新 token 输出时侧栏、模型选择器、历史列表不重绘闪烁。
- 长代码回答生成时页面不卡死。

---

### 2.2 输入区稳定性

#### 当前重点

输入区是用户对“顺不顺”的第一感知点，需要避免发送、上传、切模型、切技能时出现跳动或状态混乱。

#### 优化方向

| 优化项 | 说明 | 优先级 |
|---|---|---|
| 输入框高度平滑增长 | 多行输入不突然顶起消息区 | P0 |
| 中文输入法稳定 | composition 期间 Enter 不误发送 | P0 |
| 发送乐观展示 | 点击发送后立即出现用户消息，不等待后端返回 | P0 |
| 上传状态独立 | 上传中/解析中/可发送/失败状态分离 | P0 |
| 粘贴文件即时预览 | 图片、PDF、文档粘贴后立即显示卡片 | P0 |
| 模型/技能切换不重绘输入框 | composer 与外部选择状态解耦 | P0 |

#### 验收标准

- 输入中文时不误触发发送。
- 上传多个文件时仍可继续输入。
- 发送后输入框立即清空并保持可输入。
- 切换模型不会导致输入内容丢失。

---

### 2.3 统一 Loading / Skeleton

#### 问题

纯 spinner 会让用户感觉“卡住了”；页面骨架塌陷会显得粗糙。

#### 建议统一以下骨架屏

| 页面/区域 | Skeleton 内容 |
|---|---|
| 聊天历史 | 历史条目骨架，保留侧栏宽度 |
| 消息列表 | 对话气泡骨架，保持消息区布局 |
| 模型列表 | 模型卡片/下拉项骨架 |
| 文件列表 | 文件卡片骨架 |
| 技能市场 | 技能卡片骨架 |
| 图片生成记录 | 图片网格骨架 |
| 用户中心 | 数据卡片骨架 |

#### 验收标准

- 页面切换时主布局不塌陷。
- 加载状态只影响局部区域，不阻塞整个页面。
- 尽量少使用全屏 loading。

---

### 2.4 前端状态拆分

#### 原则

高频状态不要放在顶层 layout 或 chat page 中集中管理，否则会扩大重渲染范围。

#### 建议拆分

| 状态域 | 建议 |
|---|---|
| 当前会话 | 单独 conversation store |
| 消息列表 | 独立 message store，按 conversation id 分区 |
| 流式 token | 独立 streaming store，只更新当前消息 |
| 输入区 | composer local state，避免依赖全局大对象 |
| 上传状态 | upload queue store |
| 模型选择 | model preference store |
| sidebar 历史 | sidebar store，与消息流解耦 |
| toast/modal | UI store，不影响聊天主体 |

#### 验收标准

- token 流式更新不触发 sidebar 重新渲染。
- 上传状态变化不触发整个消息列表重绘。
- 用户信息/额度刷新不打断正在输入或生成。

## 3. P0/P1：错误提示体系重构

### 3.1 错误分层

目前 AI 平台最忌讳只提示“生成失败”。建议将错误提示按用户可行动作分类。

| 场景 | 用户提示 | 建议动作 |
|---|---|---|
| 模型不可用 | 当前模型暂不可用 | 一键切换推荐模型 |
| API Key/额度不足 | 当前服务额度不足 | 稍后重试或更换模型 |
| 限流 | 当前模型请求过多 | 自动等待/重试或切模型 |
| 文件过大 | 文件超过限制 | 压缩或拆分上传 |
| 文件未解析完成 | 文件仍在解析 | 等待完成后再发送 |
| 上下文过长 | 当前上下文过长 | 新建会话/减少文件/开启摘要 |
| 网络中断 | 连接中断 | 继续重试/恢复生成 |
| 图片生成失败 | 图片生成失败 | 修改提示词或换模型 |

### 3.2 错误 UI 形态

- 消息气泡内显示可恢复错误。
- toast 只用于轻提示，不承载长错误。
- 可重试错误提供按钮。
- 不可重试错误说明原因和下一步。
- 后端原始错误不要直接暴露给普通用户。

---

## 4. P1：模型选择体验升级

### 4.1 当前问题

多模型平台的核心矛盾是：模型越多，普通用户越不知道选哪个。

### 4.2 建议能力

| 功能 | 说明 | 优先级 |
|---|---|---|
| 模型标签 | 快速、便宜、最强、长上下文、代码、中文、图像 | P1 |
| 最近使用 | 常用模型置顶 | P1 |
| 收藏模型 | 用户自定义常用模型 | P1 |
| 自动推荐 | 根据任务类型推荐模型 | P1 |
| 不可用隐藏/置灰 | 避免用户选择不可用模型 | P1 |
| 成本提示 | 发送前显示预计消耗，生成后显示实际消耗 | P1 |

### 4.3 推荐规则示例

| 用户行为 | 推荐 |
|---|---|
| 上传 PDF/长文档 | 长上下文/文档理解模型 |
| 输入代码/报错 | coding 模型 |
| 开启联网搜索 | 搜索增强表现更好的模型 |
| 选择图片附件 | 支持 vision 的模型 |
| 简单短问答 | 低成本快速模型 |

---

## 5. P1：文件能力可视化

### 5.1 目标

AI Pool 已有 Direct-First、解析文本兜底、历史文件 RAG 等能力，但前端需要让用户“看见文件正在如何被使用”。

### 5.2 建议补齐

| 功能 | 说明 | 优先级 |
|---|---|---|
| 文件状态机 | 已上传 / 解析中 / 已索引 / 可引用 / 失败 | P1 |
| 引用来源展示 | 回答旁显示使用了哪些文件和片段 | P1 |
| 指定文件回答 | “只基于这些文件回答” | P1 |
| 文件元信息 | 页数、字数、类型、是否向量化 | P1 |
| 多文件场景入口 | 合同比较、论文对比、简历筛选、财报分析 | P1 |
| 历史文件复用 | 会话内选择已上传文件作为上下文 | P1 |

### 5.3 验收标准

- 用户能知道文件是否已经可用。
- 用户能知道回答引用了哪些文件。
- 文件解析失败时有明确原因。
- 多文件任务入口不需要用户自己写复杂 prompt。

## 6. P1：会话管理生产力化

### 6.1 建议能力

| 功能 | 说明 | 优先级 |
|---|---|---|
| 会话收藏/置顶 | 高频会话快速访问 | P1 |
| 文件夹/项目 | 按项目管理会话 | P1 |
| 会话内搜索 | 搜索当前会话内容 | P1 |
| 全局会话搜索增强 | 按标题、内容、模型、技能、文件过滤 | P1 |
| 自动摘要卡片 | 长会话生成简短摘要 | P1 |
| 批量归档/删除 | 清理历史记录 | P1 |
| 分享控制 | 分享时隐藏模型、隐藏附件、隐藏系统信息 | P1 |

### 6.2 产品价值

会话管理做强后，AI Pool 会从一次性问答工具变成长期工作台。

---

## 7. P1：技能系统工作流化

### 7.1 当前方向

技能不应只是 prompt 模板列表，而应该变成“可执行工作流入口”。

### 7.2 建议能力

| 功能 | 说明 | 优先级 |
|---|---|---|
| 技能执行步骤 | 理解任务 → 检索资料 → 生成草稿 → 校验结果 | P1 |
| 技能能力说明 | 是否支持文件、联网、图片、长文档 | P1 |
| 推荐模型 | 每个技能绑定推荐模型 | P1 |
| 输入要求 | 明确告诉用户需要提供什么 | P1 |
| 输出格式预期 | 报告/表格/JSON/方案/代码 | P1 |
| 最近使用/收藏 | 高频技能快速访问 | P1 |
| 失败原因说明 | 技能失败时说明模型、参数、文件还是网络问题 | P1 |

### 7.3 UI 原则

- 不要做复杂 agent 编排画布。
- 先做清晰的技能卡片、执行过程、输入输出说明。
- 技能页要像“任务市场”，不是“prompt 仓库”。

---

## 8. P1/P2：用户中心与运营后台

### 8.1 用户中心

建议补：

- 使用量统计。
- 消耗趋势。
- 常用模型排行。
- 常用技能排行。
- 额度明细。
- 充值/套餐记录。
- API 调用记录。

优先级：P1。

### 8.2 管理后台

建议补：

- 用户列表。
- 用户额度调整。
- 模型开关。
- 模型价格配置。
- API key 池状态。
- 请求日志。
- 错误率监控。
- 成本统计。
- 单用户封禁/限流。
- 公告配置。
- 推荐模型配置。

优先级：P1/P2。

---

## 9. P2：API 平台化

AI Pool 不应只停留在网页聊天，也可以成为 AI API 网关。

建议能力：

- OpenAI-compatible API。
- 用户 API key 管理。
- 调用日志。
- token 消耗统计。
- 模型路由。
- 限流策略。
- API 文档页。
- SDK 示例。

产品意义：

> 从“AI Web 工具”升级为“AI 基础设施平台”。

---

## 10. 不建议现在优先做

| 不建议项 | 原因 |
|---|---|
| 重做复杂设计系统 | 成本高，短期收益低 |
| 大量炫酷动画 | 增加卡顿和维护成本，不符合当前简洁风格 |
| 原生移动 App | Web 体验还没完全打磨前不宜分散精力 |
| 多人协作编辑 | 实现复杂，当前不是核心痛点 |
| 复杂 Agent 可视化编排 | 容易变成演示型功能，真实使用门槛高 |
| 自训练模型平台 | 偏离 AI Pool 聚合/网关/工作台定位 |
| 一次性重构所有页面 | 风险大，应按主链路逐步治理 |

---

## 11. 建议实施路线

### 第一阶段：体验性能专项（1-2 周）

目标：减少卡顿、闪烁、跳动。

1. 聊天列表性能优化。
2. Markdown / 代码块渲染优化。
3. 输入区稳定。
4. 上传状态独立。
5. loading/skeleton 统一。
6. 错误提示分层。

### 第二阶段：生产力增强（2-4 周）

目标：让用户更愿意长期使用。

1. 会话收藏、归档、搜索。
2. 模型标签、推荐、收藏。
3. 文件引用可视化。
4. 技能工作流化。
5. 用户使用统计。

### 第三阶段：平台化能力（1-2 月）

目标：支持商业化、B2B、开发者接入。

1. 管理后台。
2. OpenAI-compatible API。
3. 用户 API key。
4. 成本、日志、限流。
5. 多租户/白标配置。

---

## 12. 最优先 Top 10

1. 聊天消息列表虚拟化。
2. 流式消息局部更新，避免全页重渲染。
3. Markdown / 代码块缓存与懒渲染。
4. 输入框、上传、发送链路稳定化。
5. 统一 skeleton，减少页面跳动。
6. 错误提示体系重构。
7. 模型标签、推荐、收藏、最近使用。
8. 文件解析/索引/引用状态可视化。
9. 会话收藏、搜索、归档、文件夹。
10. 技能从模板入口升级为任务工作流入口。

---

## 13. 结论

AI Pool 当前最值得投入的方向是：

> **用前端性能治理和状态可视化，把已有后端能力包装成稳定、清晰、低认知负担的 AI 工作台。**

只要聊天、文件、模型、技能四条核心链路足够顺，AI Pool 的产品质感会明显提升；后续再补管理后台和 API 平台化，商业化路径会更清晰。

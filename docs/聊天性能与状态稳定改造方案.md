# 聊天性能与状态稳定改造方案

> 适用项目：AI Space / AI-Pool WebUI  
> 目标范围：`frontend` 聊天主链路、流式输出、消息渲染、消息运行态、任务恢复/轮询边界  
> 当前结论：项目已经具备外部 streaming store 雏形，后续优化应以“增强运行时状态层 + 拆分重渲染组件 + 完成态统一收敛”为主，而不是推倒重写。

---

## 1. 背景与判断

当前聊天体验相关的主要问题集中在两类：

1. **性能问题**
   - 长对话、长 Markdown、长代码块、ECharts、数学公式等内容容易导致渲染压力过大。
   - 流式阶段如果频繁触发 React 主消息状态更新，会造成 `MessageList`、输入框、侧边栏等不必要重渲染。
   - 当前 `frontend/components/chat/MessageList.tsx` 体量较大，职责过多，后续维护和性能定位成本高。
   - 当前 `frontend/components/chat/MarkdownRenderer.tsx` 直接集成 `react-markdown`、`remark-math`、`rehype-katex`、`react-syntax-highlighter`、`EChartsBlock`，属于高成本渲染点。

2. **状态稳定问题**
   - 搜索、生成、思考、后台任务、错误、停止、完成等状态来源较多。
   - 流式 task stream、DB polling、最终消息写回之间如果缺少统一收敛规则，容易出现旧数据覆盖 live 内容、完成后仍显示生成中、报错后状态残留等问题。
   - `frontend/hooks/useChat.ts` 体量较大，承担发送、SSE/task stream、polling、分页、compare、恢复等职责，长期继续堆逻辑风险较高。

调研对照了另一个项目 `AMC-WebUI` 的聊天实现，其核心模式验证了本项目改造方向是正确的：

- 高频 token 不直接进入 React 主消息状态，而进入外部 streaming store。
- 每条消息组件单独订阅自己的流式数据。
- 用 `requestAnimationFrame` 合并通知，避免每 token 触发大量 React 更新。
- 完成时再将最终内容和元数据写入持久消息状态。
- Markdown、代码块、图表、数学渲染需要 lazy / memo / deferred。
- 发送、stream handler、lifecycle、finalizer、message reducer 应有明确边界。

## 2. 总体原则

### 2.1 状态分层

```text
messages state：低频、持久、最终态
streaming.ts：高频、临时、运行态
```

`messages state` 负责：

- 历史消息列表
- 已完成 assistant content
- server message id
- conversation id
- persisted metadata
- usage / credits / completedAt / stopped / error 等最终态

`streaming.ts` 负责：

- 流式 content delta
- reasoning / thinking delta
- 搜索中、文件检索中、生成中、收尾中等运行态
- 当前 task id / background task id / request id
- 当前错误临时态
- 当前 sources / search count 临时态

### 2.2 高频更新不进主消息列表

流式阶段：

```text
后端 token/event
↓
realtimeAppend / realtimeUpdate
↓
当前 assistant message 组件订阅并刷新
```

不要每个 token 都：

```ts
setMessages(prev => prev.map(...))
```

### 2.3 完成时统一 finalization

完成阶段：

```text
SSE/task stream completed
↓
必要时等待 DB/task final state
↓
finalizeAssistantMessage
↓
最终 content/reasoning/status 写回 messages state
↓
realtimeClear(messageId)
```

### 2.4 流式阶段降级渲染

流式阶段不应完整执行高成本渲染：

- 代码高亮
- ECharts 初始化
- KaTeX / MathJax 类数学渲染
- Mermaid / Graphviz 图形渲染
- 大表格完整布局

第一阶段建议：

```text
streaming：纯文本或轻量 Markdown
completed：完整 Markdown / CodeBlock / ECharts / Math
```

后续可做进阶模式：流式阶段支持基础 Markdown，但对敏感内容自动 bypass。

## 3. 已确认需要优化的 top 项

### 3.1 增强 `frontend/lib/streaming.ts`

当前已有：

- `store = new Map<string, RealtimeData>()`
- `subs = new Map<string, Set<() => void>>()`
- `pending = new Set<string>()`
- `requestAnimationFrame` 合并通知
- `realtimeAppend`
- `realtimeUpdate`
- `realtimeGet`
- `realtimeSubscribe`
- `realtimeClear`
- 兼容旧 API：`streamAppend`、`streamSubscribe`、`streamGet`、`streamClear`

需要补齐：

1. **TTL 清理**
   - 避免异常路径遗漏 clear 后 Map 长期残留。
   - 没有 active listener 且超时的 entry 自动回收。

2. **immutable snapshot**
   - 当前 `Object.assign(data, patch)` 为原地 mutate。
   - 应改为 `store.set(id, { ...prev, ...patch })`。
   - 让 `useSyncExternalStore` 快照引用更稳定、调试更清晰。

3. **reasoning 分离**
   - 当前主要是 `content`。
   - 新增 `reasoning` 字段，避免 thinking/reasoning 混入正文。

4. **运行态结构化**
   - 第一阶段保留旧字段兼容。
   - 新增 `phase`，逐步替代 scattered flags。

建议第一版类型：

```ts
export type RuntimePhase =
  | "idle"
  | "starting"
  | "thinking"
  | "searching"
  | "retrieving_files"
  | "generating"
  | "finalizing"
  | "completed"
  | "stopped"
  | "failed";

export type RealtimeData = {
  content: string;
  reasoning: string;

  phase?: RuntimePhase;

  activityStatus?: { kind: string; status: string; label: string };

  searchStatus?: "searching" | "completed" | "failed";
  searchSources?: any[];
  searchSourcesCount?: number;

  serverMessageId?: number;
  groupId?: number;
  groupIndex?: number;
  groupModels?: string[];
  userMessageId?: number;
  generationTaskId?: number;
  backgroundTaskId?: string;

  useBackground?: boolean;
  isComplexTask?: boolean;
  lastSequence?: number;
  completedAt?: number;

  errorCode?: string;
  errorMessage?: string;
  retryable?: boolean;
  requestId?: string;

  stopped?: boolean;
};
```

建议新增 API：

```ts
export function realtimeAppendContent(id: string, text: string): void;
export function realtimeSetContent(id: string, content: string): void;
export function realtimeAppendReasoning(id: string, text: string): void;
export function realtimeSetReasoning(id: string, reasoning: string): void;
export function realtimeSetPhase(id: string, phase: RuntimePhase): void;
export function realtimeSweepExpiredEntries(now?: number): void;
```

兼容旧 API：

```ts
export function realtimeAppend(id: string, text: string) {
  realtimeAppendContent(id, text);
}

export function streamAppend(id: string, delta: string) {
  realtimeAppendContent(id, delta);
}
```

### 3.4 拆分 `MessageList.tsx`

当前文件：

```text
frontend/components/chat/MessageList.tsx
```

目标是将其从“所有消息 UI 的大文件”收敛为列表容器。

建议结构：

```text
frontend/components/chat/message/
├── MessageVirtualList.tsx
├── MessageRow.tsx
├── UserMessageBubble.tsx
├── AssistantMessageBubble.tsx
├── MessageText.tsx
├── StreamingAnswer.tsx
├── PlainStreamingText.tsx
├── ReasoningBlock.tsx
├── MessageActions.tsx
├── MessageSources.tsx
├── MessageFiles.tsx
├── MessageErrorBlock.tsx
├── CompareMessageSwitcher.tsx
├── types.ts
└── utils.ts
```

关键原则：

1. `MessageList.tsx` 只负责列表、虚拟滚动、加载更多、空状态。
2. `MessageRow` 使用 `React.memo`。
3. `AssistantMessageBubble` 内部调用 `useMessageRealtime(message.id)`。
4. 高频 realtime 更新只影响当前 assistant bubble。
5. 不向 `MessageRow` 传入大型不稳定对象，如完整 models array、大 Map、临时匿名函数。

示例：

```tsx
export const MessageRow = memo(function MessageRow(props: MessageRowProps) {
  if (props.message.role === "user") {
    return <UserMessageBubble {...props} />;
  }

  if (props.message.role === "assistant") {
    return <AssistantMessageBubble {...props} />;
  }

  return null;
}, areMessageRowEqual);
```

比较函数应尽量基于 primitive / stable props：

```ts
function areMessageRowEqual(prev: MessageRowProps, next: MessageRowProps) {
  return (
    prev.message.id === next.message.id &&
    prev.message.content === next.message.content &&
    prev.message.completedAt === next.message.completedAt &&
    prev.message.stopped === next.message.stopped &&
    prev.message.errorCode === next.message.errorCode &&
    prev.isStreaming === next.isStreaming &&
    prev.isSelected === next.isSelected &&
    prev.groupActiveIndex === next.groupActiveIndex
  );
}
```

```ts
export function shouldApplyPolledContent(input: {
  streamActive: boolean;
  liveContent: string;
  dbContent: string;
  taskStatus?: string;
}): boolean {
  if (input.streamActive) return false;
  if (!input.dbContent.trim()) return false;
  if (input.dbContent.length < input.liveContent.length) return false;
  return input.taskStatus === "completed";
}
```

目的：

- DB polling 不覆盖正在流式显示的内容。
- completed/finalizing/error/stopped 统一处理。
- task stream 与 polling 的时序由明确函数裁决。

## 5. 关键实现细节

### 5.1 `streaming.ts` 推荐内部实现

```ts
const store = new Map<string, RealtimeData>();
const subs = new Map<string, Set<() => void>>();
const touchedAt = new Map<string, number>();
const pending = new Set<string>();
let frame: ReturnType<typeof requestAnimationFrame> | null = null;

const REALTIME_ENTRY_TTL_MS = 5 * 60_000;
```

统一更新函数：

```ts
function updateEntry(id: string, updater: (prev: RealtimeData) => RealtimeData) {
  realtimeSweepExpiredEntries();

  const prev = store.get(id) ?? { content: "", reasoning: "" };
  const next = updater(prev);

  store.set(id, next);
  touchedAt.set(id, Date.now());
  schedule(id);
}
```

内容更新：

```ts
export function realtimeAppendContent(id: string, text: string) {
  if (!text) return;
  updateEntry(id, (prev) => ({
    ...prev,
    content: prev.content + text,
  }));
}

export function realtimeAppendReasoning(id: string, text: string) {
  if (!text) return;
  updateEntry(id, (prev) => ({
    ...prev,
    reasoning: prev.reasoning + text,
  }));
}

export function realtimeUpdate(id: string, patch: Partial<RealtimeData>) {
  updateEntry(id, (prev) => ({
    ...prev,
    ...patch,
  }));
}
```

TTL sweep：

```ts
export function realtimeSweepExpiredEntries(now = Date.now()) {
  for (const [id, lastTouched] of touchedAt.entries()) {
    const listeners = subs.get(id);
    const hasActiveListeners = !!listeners && listeners.size > 0;

    if (now - lastTouched <= REALTIME_ENTRY_TTL_MS) continue;
    if (hasActiveListeners) continue;

    store.delete(id);
    touchedAt.delete(id);
    pending.delete(id);

    if (listeners?.size === 0) {
      subs.delete(id);
    }
  }
}
```

clear：

```ts
export function realtimeClear(id: string) {
  store.delete(id);
  touchedAt.delete(id);
  pending.delete(id);

  const listeners = subs.get(id);
  if (listeners?.size === 0) {
    subs.delete(id);
  }

  if (pending.size === 0 && frame !== null) {
    cancelAnimationFrame(frame);
    frame = null;
  }
}
```

### 5.2 流式渲染选择

```tsx
const realtime = useMessageRealtime(isStreaming ? message.id : "");

const displayContent = isStreaming
  ? realtime?.content || message.content
  : message.content;

const displayReasoning = isStreaming
  ? realtime?.reasoning || message.reasoning
  : message.reasoning;
```

### 5.3 finalization 规则

完成时统一处理：

```ts
finalizeAssistantMessage({
  message,
  realtime,
  dbMessage,
  taskStatus,
  usage,
  error,
});
```

内容选择优先级建议：

```text
1. completed DB content，且长度 >= live content
2. live realtime content
3. existing message content
```

错误优先级：

```text
explicit error > stopped > completed > finalizing > generating
```

## 6. 验收标准

### 6.1 性能验收

- 200+ 历史消息打开不卡顿。
- 500+ 消息滚动和向上加载不明显掉帧。
- 长回答流式输出时：
  - 输入框不失焦。
  - sidebar 不闪。
  - 模型选择器不重绘。
- 5000+ 字 Markdown 完成后渲染可接受。
- 300 行代码块不会卡死页面。
- ECharts 不在流式阶段初始化。

### 6.2 状态验收

- 搜索中 → 搜索完成 → 生成中 → 完成，状态顺序稳定。
- 报错后不残留“生成中/搜索中”。
- 用户停止生成后不再显示 running。
- 刷新页面后 completed 状态正确。
- 切会话回来后后台任务能恢复或显示最终状态。
- polling 不覆盖正在流式显示的内容。
- DONE 后如果 DB 内容延迟，UI 显示“正在收尾”而不是突然空掉。

### 6.3 内存验收

- 连续生成多轮后 runtime store 不持续增长。
- 异常中断的 stream 过 TTL 后可回收。
- listener 不大量残留。

8. 中途停止。
9. 重新生成。
10. 切换会话再回来。
11. 刷新页面恢复。
12. compare 多模型对比。
13. provider 限流/报错。
14. DB polling 延迟或返回旧内容。

---

## 8. 当前建议执行顺序

```text
1. streaming.ts：TTL + immutable snapshot + reasoning 分离
2. MarkdownRenderer：lazy/memo/code collapse/ECharts lazy
3. useSmoothStreaming：流式降频与敏感内容 bypass
4. MessageList：拆 MessageRow/AssistantBubble/UserBubble/Actions/Reasoning
5. messageStatus：统一状态派生
6. useChat：拆 task stream / polling / finalizer / reducer
```

短期第一轮优先做 1-3，收益明显且风险可控。

---

## 9. 不建议第一阶段做的事

- 不建议第一阶段重写后端 stream 协议。
- 不建议第一阶段大规模改数据库消息表。
- 不建议第一阶段直接把 `useChat.ts` 全部重构。
- 不建议同时改聊天渲染、任务恢复、计费、模型选择等多个大模块。
- 不建议在流式阶段启用完整 Markdown + 代码高亮 + ECharts + 数学渲染。

---

## 10. 最终目标状态

最终实现后，聊天主链路应达到：

```text
高频 token/event -> streaming.ts runtime store
当前 message bubble 单独订阅 runtime snapshot
流式阶段轻量渲染和平滑展示
完成阶段 finalizeAssistantMessage 写回 messages state
Markdown/Code/ECharts 只在合适时机重型渲染
状态展示由 deriveMessageStatuses 统一派生
useChat 只做编排，stream/polling/finalizer 各自独立
```

这套改造的核心价值是：

1. **性能更稳**：长回答和长历史不拖慢整个页面。
2. **状态更准**：搜索、生成、停止、失败、完成不乱跳。
3. **代码更可维护**：后续 RAG 引用、任务通知、工具调用、Deep Research 都能接入同一运行态体系。
4. **风险可控**：先增强已有机制，再逐步拆分，不推倒重写。
